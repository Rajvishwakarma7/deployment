# AWS S3 Setup

This guide explains how to create and configure an AWS S3 bucket for backend file storage.

The same approach can be reused for other projects that need to store files such as images, documents, audio, or other uploads.

---

# 1. Architecture

The backend application runs on AWS EC2 and uses Amazon S3 for object storage.

```text
Client
   |
   v
Node.js API
   |
   | AWS SDK
   v
Amazon S3
   |
   v
Files / Objects
```

The application should not store important uploaded files only inside the Docker container.

S3 provides durable object storage independent of the EC2 container lifecycle.

---

# 2. Create an S3 Bucket

Open the AWS Console and go to:

```text
S3
```

Choose:

```text
Create bucket
```

Select the AWS Region where the application is deployed or the region you intentionally want to use.

Example:

```text
ap-south-1
```

Use a globally unique bucket name, for example:

```text
william-hazlitt-production
```

Bucket names must be unique within AWS S3.

---

# 3. Block Public Access

For a normal backend upload system, keep:

```text
Block all public access
```

enabled.

Do not make the entire bucket public just because the application needs to upload or download files.

If files need to be publicly accessible, use a deliberate architecture such as:

- Presigned URLs
- CloudFront
- Controlled bucket policies

---

# 4. Object Ownership

Use:

```text
Bucket owner enforced
```

when creating the bucket unless the application has a specific legacy requirement for ACLs.

Avoid depending on object ACLs for normal application access.

---

# 5. Bucket Versioning

Versioning is optional.

Enable it when the application needs protection against accidental overwrites or deletes.

For simple temporary uploads, versioning may not be necessary.

---

# 6. Default Encryption

Keep S3 server-side encryption enabled.

For most applications, the default S3-managed encryption is sufficient.

For applications with stricter compliance requirements, AWS KMS can be used instead.

---

# 7. IAM Access

The backend needs permission to access the bucket.

Prefer an IAM role attached to the EC2 instance when possible.

This avoids storing long-lived AWS access keys on the server.

Recommended production architecture:

```text
EC2
 |
 | IAM Role
 v
S3 Bucket
```

If an IAM role cannot be used and access keys are required, store them as protected environment variables or secrets.

Never commit AWS credentials to GitHub.

---

# 8. Minimum S3 Permissions

The backend should receive only the permissions it actually needs.

For example, if the application needs to upload, read, and delete objects:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME/*"
    }
  ]
}
```

Replace:

```text
YOUR_BUCKET_NAME
```

with the actual bucket name.

If the application needs to list objects, add:

```text
s3:ListBucket
```

with the bucket resource:

```text
arn:aws:s3:::YOUR_BUCKET_NAME
```

Do not automatically grant:

```text
s3:*
```

unless there is a specific reason.

---

# 9. Environment Variables

The backend may use variables such as:

```text
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
AWS_REGION=
AWS_BUCKET_NAME=
```

Example:

```text
AWS_REGION=ap-south-1
AWS_BUCKET_NAME=william-hazlitt-production
```

Do not put real credentials in:

```text
.env.example
```

Use empty placeholders instead:

```text
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
AWS_REGION=
AWS_BUCKET_NAME=
```

The actual production `.env` must remain private.

# 10. Node.js AWS SDK

Install the AWS S3 SDK if the project does not already have it:

```bash
npm install @aws-sdk/client-s3
```

For presigned URLs:

```bash
npm install @aws-sdk/s3-request-presigner
```

---

# 11. Basic S3 Client

Example:

```javascript
import { S3Client } from "@aws-sdk/client-s3";

const s3 = new S3Client({
  region: process.env.AWS_REGION,
});
```

When running on EC2 with an IAM role, the AWS SDK can automatically obtain credentials from the EC2 instance role.

This is preferred over hardcoding credentials.

---

# 12. Upload an Object

Example:

```javascript
import { PutObjectCommand } from "@aws-sdk/client-s3";

await s3.send(
  new PutObjectCommand({
    Bucket: process.env.AWS_BUCKET_NAME,
    Key: "uploads/example.jpg",
    Body: fileBuffer,
    ContentType: "image/jpeg",
  })
);
```

The object will be stored under:

```text
uploads/example.jpg
```

---

# 13. Download an Object

Example:

```javascript
import { GetObjectCommand } from "@aws-sdk/client-s3";

const result = await s3.send(
  new GetObjectCommand({
    Bucket: process.env.AWS_BUCKET_NAME,
    Key: "uploads/example.jpg",
  })
);
```

For APIs, the application can return the file directly or generate a controlled download URL.

---

# 14. Delete an Object

Example:

```javascript
import { DeleteObjectCommand } from "@aws-sdk/client-s3";

await s3.send(
  new DeleteObjectCommand({
    Bucket: process.env.AWS_BUCKET_NAME,
    Key: "uploads/example.jpg",
  })
);
```

---

# 15. Presigned URLs

For private files, prefer presigned URLs instead of making the bucket public.

Example:

```javascript
import { GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const command = new GetObjectCommand({
  Bucket: process.env.AWS_BUCKET_NAME,
  Key: "uploads/example.jpg",
});

const url = await getSignedUrl(s3, command, {
  expiresIn: 3600,
});
```

The URL will expire after the configured time.

---

# 16. S3 CORS

S3 CORS is only needed when the browser directly communicates with S3.

For example:

```text
Browser
   |
   +------> S3 directly
```

If the browser sends the file to your backend and the backend uploads it to S3:

```text
Browser
   |
   v
Backend API
   |
   v
S3
```

S3 CORS may not be required for the upload itself.

If direct browser uploads are used, configure CORS for the exact frontend origin rather than allowing every origin.

Example concept:

```json
[
  {
    "AllowedOrigins": [
      "https://YOUR_FRONTEND_DOMAIN"
    ],
    "AllowedMethods": [
      "GET",
      "PUT",
      "POST"
    ],
    "AllowedHeaders": [
      "*"
    ]
  }
]
```

Adjust this according to the actual application requirements.

---

# 17. Folder Structure

S3 does not use traditional folders.

Keys can be organized using prefixes:

```text
uploads/
    users/
        123/
            profile.jpg

uploads/
    documents/
        456/
            document.pdf
```

Example object key:

```text
uploads/users/123/profile.jpg
```

This makes objects easier to organize.

---

# 18. Security Best Practices

- Keep Block Public Access enabled.
- Prefer EC2 IAM roles over long-lived access keys.
- Follow least-privilege IAM permissions.
- Never commit AWS credentials.
- Do not put credentials inside Docker images.
- Use HTTPS for application communication.
- Use presigned URLs for controlled private downloads.
- Restrict CORS to trusted origins.
- Enable versioning when appropriate.
- Enable encryption.
- Consider lifecycle rules for temporary files.
- Monitor unusual S3 access.

---

# 19. Lifecycle Rules

If the application stores temporary files, configure an S3 lifecycle rule.

Example:

```text
temporary/
```

Objects under this prefix can be automatically deleted after a defined period.

This helps control storage costs.

Choose the retention period based on the application's actual requirements.

# 20. Testing From EC2

If using an IAM role, verify AWS identity:

```bash
aws sts get-caller-identity
```

If the AWS CLI is installed.

Check the bucket:

```bash
aws s3 ls s3://YOUR_BUCKET_NAME
```

Upload a test file:

```bash
echo "S3 test" > test.txt

aws s3 cp test.txt s3://YOUR_BUCKET_NAME/test.txt
```

Verify:

```bash
aws s3 ls s3://YOUR_BUCKET_NAME/
```

Delete the test object:

```bash
aws s3 rm s3://YOUR_BUCKET_NAME/test.txt
```
